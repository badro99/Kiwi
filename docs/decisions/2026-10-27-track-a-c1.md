# Decisions · track A and the first C1 wave (27 October 2026)

Each ruling below changes behaviour somewhere and can be reversed. The lead (Claude) made them under the owner's approval of the structure plan on 26 October ("approved, start with track A").

## Where the till and the server disagreed, the server wins

Moving each rule into one module exposed places where the browser and the server computed different answers. In every case the server's rule was kept, because the server is what the books record.

- **Loyalty refunds:** the till estimated points to take back at today's rate. The server uses the points the sale actually earned, with a capped cumulative prorata. The till now shows what the server will do.
- **Catalogue compaction:** the browser compacted the movement journal after 45 days or 12,000 movements. The server compacts at 11,000, targets 10,000 and protects reservations and time boundaries. The 45-day rule is gone.
- **Menu modifiers and recipe units:** one difference each, shown by a test that failed on the old code, aligned on the server's normalisation.

## Staff codes: one canonical value

Team and employee-access documents kept a staff code in two fields, `pinCode` and `password`. A read-only production check on 26 October found 108 members in 13 stores and none with differing fields.

- The canonical value is `pinCode`, falling back to `password` when `pinCode` is empty. That is exactly what the three server verifiers already did, so nobody's access changes.
- Every server write now stores both fields equal.
- The staff editor prefills from the canonical value.
- Both fields stay redacted for anyone who isn't the owner or an operator. Removing `password` entirely is a later step, once no cached dashboard still reads it.

## Onboarding: the kit path now refuses what the live path refuses

The onboarding wizard has two renderers: the live default and a kit version used only behind a dashboard skin flag. They now share one state and submission owner. Six differences were found, and the live path's behaviour now applies to both:

1. A blank owner name at the final step: the kit accepted it, now both refuse.
2. A blank business name at the final step: same.
3. A malformed staff code for a non-owner: the kit ignored it, now both refuse.
4. A reserved staff code for a non-owner: same.
5. A duplicate staff code for a non-owner: same.
6. An invalid goal restored at the final step: the kit refused it, now both submit with goal zero, as the live path did.
